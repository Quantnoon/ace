# MT5 Connection Instructions

## Connection First

This file applies to the trading workflow in [AGENTS.md](../AGENTS.md), not repository maintenance. Normal use starts with Ace open in an AI client whose MT5 MCP is already connected and execution-enabled. Reuse that access and verify it automatically through the selected client's actual MCP interface; tool names and setup formats differ between clients and servers. Technical access alone is not a user request to trade.

For ordinary session startup or reconnection, also follow [Automatic Dashboard](../AGENTS.md#automatic-dashboard): start or reuse the local viewer through the client's background-process facility without asking the user to run it. Honor explicit connection-only requests. Viewer startup must not hold up required checks or emergency protection, and its local readiness response never verifies MT5 connectivity or account identity.

1. Discover tools/resources already exposed to the client. Read the actual MT5 server's account, market-data and execution schemas and documentation without another MCP-access confirmation. Do not invent tool names, parameters, transports, or a health API.
2. If a candidate MT5 connection exists, make a documented read-only account/terminal request. A server name, saved configuration, TCP response, or health message alone is not proof of capability.
3. Reuse a working verified connection and its existing execution permissions without repeating setup or asking for credentials. Only if required configuration is missing or unusable, ask for the missing endpoint information, including its documented path. Do not guess a `/mcp` or other suffix. Reuse valid nonsecret connection inputs after a transient outage rather than requesting new secrets unnecessarily.
4. Only if authentication is missing, obtain the access token through the client's secure secret store, trusted user configuration outside the repository, or supported environment mechanism. Ask only for the missing secure-configuration fact, never for a token pasted into chat. If the client has no secure way to supply it, report the blocker.
5. Use the selected server's documented remote MCP transport and authentication. Use `Authorization: Bearer <access token>` only if the server specifies bearer authentication. Verify endpoint identity and certificate validation; require HTTPS except explicitly approved loopback HTTP. Never forward credentials to unapproved endpoints or redirects, or use a token embedded in a URL/query string.
6. If the client cannot add a connection dynamically, guide the user through its own MCP setup and required reload/restart. Do not create vendor-specific configuration in this repository. Obtain permission before changing external host settings, preserve unrelated settings, and do not grant blanket tool permissions.
7. Discover the newly exposed tools and repeat the authenticated read-only verification. Report an MT5 account connected only when actual account access succeeds, then follow the handoff below.

Do not assume any particular environment-variable interpolation syntax, JSON configuration format, slash command, secret UI, or automatic `.env` loading. A config edit is not a connection. Do not install a trading bridge or call ad-hoc price/order HTTP endpoints as a fallback.

## Post-Connection Handoff

For a request to connect or reconnect to the MT5 MCP without a connection/status-only qualification, once authenticated read-only access verifies the account login plus broker server, demo/live type, and currency, report that identity and continue to the next incomplete onboarding step in the same response. Accept the monetary budget and target together; ask only for missing or ambiguous amounts/currency under [Monetary Risk And SQLite/Helper Contract](risk-management.md). These are the only user-supplied trading settings. This also applies when reusing an already-working connection. Do not end with only "connected", require a separate setup request, or ask whether to begin collecting inputs. Honor the explicit read-only exceptions in `AGENTS.md` without starting onboarding.

In an explicit trading context, supplying the complete positive budget and target authorizes the documented MT5 operations for that verified account task, including the final missing input after a trading-start request. This is not unrelated/admin access, a host-permission change or a bypass of a denied tool. Record the actual trusted user request, not an invented approval. Do not ask for final named-account confirmation, per-order approval or a keep-going choice when intent, account, amounts and scope are unambiguous. Ask only for a genuinely missing or ambiguous fact. Drafts, examples, analysis-only, progress-only, maintenance and connection-only requests do not authorize trading; enabled MCP tools and saved amounts do not supply that intent.

For trading onboarding, reconcile existing `ace_state.sqlite3` through `scripts/account_check.py` before reusing or updating inputs. Read `status` for canonical control/unresolved intents and bounded `context` for completed originals, related actions and linked assessments; both are private cached reads, not current account verification. Reuse verified same-account monetary drafts only as drafts, and verify real approval provenance before reusing a mandate. A missing database is unconfigured; a different account binding or corrupt/unsupported state requires the risk instructions' recovery rules, not silent replacement or copied approval. No legacy account-file detection or import is part of this workflow. Transport/configuration/health without authenticated account verification must not trigger account-bound setup; report missing MCP/secure-secret capabilities as connection blockers.

Missing broker/instrument calendars, market data, or execution capabilities does not by itself prevent saving monetary drafts for the verified account. Keep affected new exposure blocked without treating a draft as authority or requiring another confirmation of an already explicit request. Follow [Goals And Progress](goals.md#compact-trading-report): routine reports belong in the local dashboard; when chat is needed for a missing input or actual blocker, give concise verified source times, unavailable values, limits/latches and the permitted next step. Do not delay separately still-authorized, identity-verified emergency reductions for onboarding questions or helper/database repair.

Prepare the verified capability/universe proposal and save the complete monetary and mandate `draft`. Ace derives and discloses the named account, eligible broker symbols, snapshot freshness limit, entry timeframe, safety margin, any latch-only interval, observed-only limits, Ace-owned management and whole-account loss/target closures including manual exposure under the start contract. These technical choices are not additional user settings or authority to change money, reset risk or expand existing scope. Full current trade analysis, protection, costs and affordability remain mandatory before entries, never invented to justify activation.

For a direct explicit request, use `activate` with `approval_mode: "start_request"`, `approval_ref` identifying that actual trusted request and `approved_at` its actual timestamp. Capture and activate promptly after preparing the proposal, without a human review delay. The baseline must be at or after the request, fresh at activation, and no later than the fresh current snapshot. An omitted `approval_mode` retains `reviewed` behavior only for a real historical reviewed receipt: preserve its frozen baseline, even when historical, and obtain fresh post-approval data. Never rewrite an old receipt as new start authority. Follow the exact [activation contract](risk-management.md#mandate-and-activation).

After successful activation, handle any activation-time emergency first. Then `session start` for genuinely authorized ongoing work, reuse an active session, or `session resume` only for verified interrupted-task recovery under [task control](goals.md#final-result-and-resume). Obtain a separate fresh snapshot and call the first `cycle` before normal management/entries, even with no signal. Follow [Loop Sessions](loop.md) through observation, management and eligible entries until an observed budget/target latch, then verified liquidation/reconciliation. Consume source-bound journal revisions and canonical control, and actually wait/read again. No fills, unchanged orders, a completed batch or saved report is completion; settlement still leaves an active user session monitoring. Old bounded/reviewed authority is not expanded, and explicit bounded/read-only requests do not start sessions.

## Market Data And Instrument Discovery

Market analysis uses documented read-only MCP tools only. A quote, bar, or symbol-inventory read must be an actual authenticated response with its source timestamp; configuration, a health response, or an earlier session's memory verifies nothing.

1. List the broker's tradable symbols and keep the majors, major minors, metals, oil and other commodities, indices, and synthetics that actually exist on this account. Typical candidates include the major FX pairs, liquid minors such as EURJPY, GBPJPY, and AUDJPY, spot metals such as XAUUSD and XAGUSD, energy contracts such as WTI/Brent, index CFDs, and the broker's synthetic instruments.
2. For each candidate, verify asset/contract type, contract size, tick value and precision, account-currency conversion, volume minimum/maximum/step, stop and freeze distances, typical spread, commission, swap/financing, current margin requirement, and trading availability.
3. For the FX entry regime screen, playbooks, and strategy-specific market evidence, follow [FX Entry Strategies](strategies.md). The screen gates new entries only; it never skips required management of existing positions or orders.
4. For FX pairs that pass the strategy screen, and for other eligible asset classes, read the current quotes and timeframes needed to describe direction/range, higher-timeframe bias, momentum, volatility, spread quality relative to the planned stop, session, and any scheduled event that could invalidate the read.
5. Exclude symbols whose economics, conversion, or protective-stop support cannot be verified. Class-level scope is not per-symbol approval. Do not infer contract type, affordability, conversion, or market hours from a symbol name, assume a single forex calendar across asset classes, or assume 24/7 trading outside verified crypto/CFD hours.

For new FX entries, use [FX Entry Strategies](strategies.md) as the single source for regime screening, individual playbooks, and per-signal rationale/reporting. Apply [risk management](risk-management.md#before-each-risk-increase) and this file's instrument-capability checks to each signal; a qualifying pattern does not waive them.

Prices must come through actual documented MT5 MCP operations, not ad-hoc endpoints or a credential-bearing Python bridge. Unknown costs are not zero. Missing essential economics, minimum-lot affordability, or execution capabilities block the affected entry, not the whole analysis.

## Secret Handling

- Tokens must never enter SQLite, Markdown, Git, repository files, reports, URLs, or diagnostic logs. Do not print secret environment values or resolved host configuration just to check connectivity.
- Redact authentication headers and sensitive query values from errors before reporting. Request only the endpoint and authentication needed for this MT5 server, not unrelated credentials.
- If a user pastes a token into chat, do not repeat or persist it. Advise rotation if it has been exposed and request secure replacement. Do not claim that prior chat/log exposure has been erased.
- An ignored credential file is not a secure secret store. Keep actual credentials outside this repository and within the user's trusted client mechanism.

The actual start request or applicable existing authority covers the exact named account, authorized universe, monetary baselines, normal management, loop cadence/recovery and both whole-account closure mandates, including manual exposure and host/observed-only limitations. Verify and disclose these facts without another final-account or routine per-action approval gate.

| Timing / observation | Verified source times, timezone/DST/calendar interpretation, freshness bounds and coherent account/history boundaries. Supply actual broker last/next candle boundaries and per-symbol closed-bar evidence under the loop contract; do not infer UTC alignment from the host clock, treat an old clock as current or reconstruct unseen peaks/midnight equity. No daily reset. |
| Exposure / ownership | Complete open positions and pending orders, including manual/other-origin orders, tickets, symbols, volume, direction, stops, execution status, and local intent bindings. Distinguish entry orders from protective/reducing orders and preserve original management bindings. |

Reconcile starting equity and history boundaries; a deposit in equity but missing from lagging history is not profit or a new adjusted peak. Read only the capabilities actually exposed. If a required value or mutation's targeting/result semantics cannot be verified, identify that blocker rather than inventing an implementation. Read-only credentials cannot execute trades; do not silently escalate access or build a new runtime service. There is no independent continuous guard, required server goal-admission service, or claim of server fencing. The local helper checks supplied snapshots only while the AI is active; it cannot guarantee a cap, return, continuous observation, or cancellation latency.

The AI client is the runtime, not a new daemon or trading bridge. Use only its actual documented continuation/wait facilities; do not add a runner, plugin or client-specific configuration. Never mark the native goal complete merely because the financial campaign is closed while the user session remains active. Helper tests or persisted state cannot make OpenCode or another client survive a final response, enforced limit or shutdown; verify actual host continuation separately under the [synthetic checks](loop.md#synthetic-continuation-checks). ## MCP Execution And Local Intents

Verify how each actual MCP mutation targets the approved login plus broker server, demo/live type, and currency. Use documented account identifiers or account-scoped connection semantics where provided and reverify the intended account before dispatch and on readback. Do not assume a default-current-account tool is safely targeted when the account or its semantics are unknown; an identity mismatch blocks that action. One active account and one local trading-agent writer are required, with ownership reverified on resumption. A read followed by local preparation cannot prevent a later terminal account switch or concurrent manual trade.

The agent, not the helper, obtains actual MCP data and verifies approval provenance. Use `scripts/account_check.py` with repository-root `ace_state.sqlite3` according to [the exact JSON/SQLite contract](risk-management.md); do not invent fields, edit SQL to manufacture authority, or treat an asserted verification flag as evidence. The helper performs no networking or trading. SQLite transactions reserve recorded headroom and one exact intention locally, not broker execution; they cannot fence other repositories/manual traders or make the check-to-dispatch interval atomic.

1. On every authorized active decision cycle, obtain a fresh verified account/exposure/history snapshot and call `cycle` for the [loop session](loop.md), even without an entry signal; use `check` for latch-only wakes, post-closure account monitoring or bounded one-shot checks. Reconcile coherent cash-flow windows, observed peak, latches, closing costs, one-writer ownership and unresolved intents. Neither command is reusable order authorization, and a bounded check does not start a session.
2. Handle monetary latches and authorized emergency reductions first, then [Active Order Management](risk-management.md#active-order-management) under original ownership/authority before new entries or winner additions. Newly prepared routine stop updates, cancellations or exits require rationale and validated root linkage in `action.context`; dispatch the exact reducing action and reconcile it, never funding an add from a proposal. Emergency context is optional and unusable metadata is dropped with a warning, not a delay to otherwise authorized protection.
3. For an eligible risk increase, verify the current market read, account-wide stressed risk, original idea-allocation/add-on conditions, broker stops, sizing/margin/costs and exact parameters. `prepare` requires complete [entry/add context](risk-management.md#decision-context) outside those MCP parameters. Verify durable recording of the original strategy or root link, rationale and account/policy/goal/symbol binding before dispatch. Do not prepare competing increases, replace original rules/allocation or silently change a prepared action.
4. Successful preparation under the approved mandate permits the actual documented MCP market/pending order or approved modification, cancellation, or close. Execute that exact action without a separate per-trade user confirmation; client tool permissions still apply. Do not stop at a passing calculation, claim execution without a tool result, invent a tool, or bypass denied access with ad-hoc HTTP.
5. Obtain post-action broker readback and verify order/ticket status, actual fills, stops, volume, remaining pending orders, and relevant history. Call `resolve` with verified outcomes; a submission acknowledgment alone is not a fill, cancellation, or flat account. Unknown outcomes and partial fills with unverified remainders stay unresolved and block further risk increases.
6. Journal the final latest accepted source and relevant intent after actual work. Consume its revision and cached canonical `session`/`loop`/`may_continue`/`loop_health`, retaining actual financial/action evidence separately. Journal never observes, moves deadlines or grants dispatch; older `state.last_result` cannot override current control. Routine explanations go to the dashboard. Actually wait/read, registering native continuation before a required yield. Reporting errors, absent fields, `may_dispatch: false` or `required_action: "none"` do not imply completion or another user decision.

Normal modifications/cancellations/closes must stay within the original authority and [active management rules](risk-management.md#active-order-management); routine management is Ace-only. Previously authorized identity-verified safety reductions do not require an entry signal or permission to add risk. Preserve original position/order bindings; classify manual exposure honestly under the whole-account closure mandate rather than inventing an owner. Use local preparation/recording when available, but helper/database failure must not delay an already-authorized identity-verified emergency reduction. Verify documented tickets/remaining-volume semantics, avoid duplicating uncertain actions, and reconcile the local record as soon as possible.

Stopped/interrupted task control blocks entries and routine management, not original-intent recovery or separately still-authorized emergency reductions. That exception never permits ignoring a user's revocation. If a stop arrives after `prepare` but before dispatch, abandon the unused ordinary dispatch permission and retain/reconcile the original intent. A stop event alone does not prove nonexecution; a local revision change is not broker-side cancellation or fencing of an in-flight request.

On every startup/resumption, recover unresolved local intents and in-flight broker requests with their original account/goal/symbol/signal binding before new exposure. Read-only `context` also recovers completed original entries and linked actions/reports after later wait notes; a prepared plan survives without a journal, but proves no execution. Missing legacy plans stay unavailable, without automatic backfill/adoption. An empty order list does not prove that a pre-crash request never executed or cannot execute later. Reconcile actual orders, deals, positions and authoritative status; do not replace an action ID or retry an ambiguous dispatch merely because no fill is visible. Missing recovery evidence blocks further increases, not separately authorized, safely targeted emergency reductions.

## Whole-Account Stops

At an observed drawdown greater than or equal to the monetary budget, or estimated account equity gain after cash-flow adjustment and incremental close costs greater than or equal to the target, latch off new risk. Under the approved mandate, cancel ALL account pending entries and close ALL account positions, including manual/other-origin exposure. Preserve protective orders until the related positions are safely closed, then reconcile remaining/orphan orders and late fills. Loss-stop handling takes precedence if both triggers apply; no entry signal is needed to perform these already-approved closures.

Read back actual cancellations, partial fills, remaining volumes/stops and positions. Financial closure requires fresh verified flat exposure, no remaining pending orders, reconciled in-flight intents and final costs, not a submitted close request. Record trigger time, pending closure, verified final net result, and any target shortfall separately under [Goals And Progress](goals.md). A target latch remains set even if slippage or late costs leave final profit below target. Reconnects, new days, equity recovery or accounting corrections never release either stop.

With an active user-controlled session, `may_continue` remains true after financial `loop.status: "closed"`. Continue fresh account-only `check` observations every five minutes or sooner for a positive latch-check interval, using accepted source/receipt evidence and `wake_reason: "monitor"`. Do not enter trades, reset the budget/target, advance candles/cycle counters or rewrite the loop ID, closure time or bar history. Late exposure returns that same financial loop to `closing` for authorized reconciliation. Session-absent legacy authority retains its original until-settlement completion; do not retrofit indefinite monitoring without genuine authority.

A new goal, policy replacement or material scope change requires explicit user instructions and reconciliation under the helper contract, not an automatic reset or a repeated confirmation of an already explicit change. Never close exposure merely to manufacture a new baseline without existing authority. A same-policy new goal preserves the risk cash-flow anchor and observed peak and cannot release a loss latch. A risk-policy reset requires an explicitly instructed replacement and retained audit history, not a new draft, missing file, or SQL edit. There is no independent service acting while the AI is inactive; observed peaks/breaches can be missed and broker stops cannot guarantee either monetary threshold.

## Reconnection And Uncertain Results

On any authentication failure, permission rejection, stale required feed, disconnect, account switch, unknown connection state, unavailable helper/state, unresolved mutation, or persistent stop, do not submit risk-increasing actions. Report blockers with last verified timestamps and financial/task stop state separately under the reporting workflow. Management requires current task authority; separately still-authorized emergency reductions require a positively verified account and documented safely targeted tools, not an entry signal or active entry permission. No continuous protection service is implied during the outage.

After reconnecting for authorized trading, reverify identity/currency, instrument calendars, exposure/protection, coherent account/cash-flow/cost history, current data, local ownership, SQLite bindings/latches, actual request/approval provenance and unresolved intents. Reuse active task control or use `session resume` only for an interrupted session's verified existing-authority host recovery, retaining its ID. Obtain one fresh snapshot after a gap, then `cycle` for active decision work or account-only `check` for closed monitoring/bounded checks; never replay missed candles. Cached `status`/`loop_health` and `session.status: "active"` prove neither account verification nor execution. An unbound legacy loop needs verified existing-authority `activate resume` for prospective binding, preserving its ID/history without another routine human approval; this does not create new task authority. Block new risk until reconciled, not authorized reductions. Recover original management evidence and retain financial anchors/latches without reconstructing unseen peaks.

Honor explicit user end by canceling scheduled continuations and recording durable `session stop`, including for legacy session-less state. Starting after a stop requires a genuinely new user request, not replayed session/control references or authority held at an earlier stop. `session resume`, `session interrupt`, activation, owner handoff and new financial goals cannot undo a stopped task. A host cancellation may prevent the local stop write; never claim it was recorded when unavailable. Reconnection alone is not a new goal, risk reset or permission to restart a stopped/bounded task.

Transient read failures use actual 5/10/20/30-second waits, capped at 30 seconds and repeated while execution remains possible, resetting after verified recovery. A failed MCP read makes no financial helper or journal call and does not itself advance revision/observation. A processed blocked helper request may consume a revision, including stale-snapshot requests; use its returned revision, or read `status` after an unknown local outcome/conflict. Do not journal outage heartbeats, refresh a source timestamp, claim an exact outage start from cached gaps, or mistake a mutation timeout for a retryable read. Record `session interrupt` only when the active task actually ceases because no permitted continuation remains, not between transient retries; that non-observing control write consumes a revision if it succeeds. Honor actual denied tools and enforced host limits. Denial of one optional action must not finish other permitted work or justify retrying/bypassing the denial.

For any mutation that times out, is interrupted, or returns an ambiguous acknowledgment:

1. Treat its execution status as unknown, not failed or successful. Freeze further risk-increasing actions.
2. Recover the durable local intent with its original account/owner/goal/symbol/signal binding and reconcile broker orders, positions, and deals using its submitted ticket/client identifier and documented result semantics, including still-in-flight requests. Request authoritative status if the result remains ambiguous; never relabel it to a new goal or symbol.
3. Retry only when the actual state and the server's documented idempotency/remaining-volume rules make the operation safe. Never blindly duplicate an entry or a close.
4. Verify actual pending-order scope/cancellation, modifications/protective stops, and position closure/remaining volume by readback, then reconcile through `resolve`. Never assume an opposite order closes a position; it may create hedged exposure or reverse a net position.
5. If liquidation is rejected, partially filled, or unavailable, report unresolved exposure and continue only verified, bounded safety actions. Do not claim that the account is flat or that a drawdown cap was preserved.

The client's permission system is a separate execution gate. Account/goal approval does not bypass it. Explain blocked tool-specific access without enabling all tools, treating a denied action as completed, or imposing routine extra per-trade user approval on an otherwise approved eligible action.
