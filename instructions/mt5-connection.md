# MT5 Connection Instructions

## Connection First

This file applies to the trading workflow in [AGENTS.md](../AGENTS.md), not repository maintenance. Use the selected AI client's MCP interface; tool names and setup formats differ between clients and servers.

1. Discover tools/resources already exposed to the client. Read the actual MT5 server's tool schemas and documentation. Do not invent tool names, parameters, transports, or a health API.
2. If a candidate MT5 connection exists, make a documented read-only account/terminal request. A server name, saved configuration, TCP response, or health message alone is not proof of capability.
3. Reuse a working verified connection. If credentials/configuration are missing or unusable, ask for the base URL and confirm the complete MCP endpoint, including its documented path. Do not guess a `/mcp` or other suffix. Reuse valid nonsecret connection inputs after a transient outage rather than requesting new secrets unnecessarily.
4. Request the access token through the client's secure secret store, trusted user configuration outside the repository, or supported environment mechanism. Ask the user to confirm that it is configured, not to paste it into chat. If the client has no secure way to supply it, report the blocker.
5. Use the selected server's documented remote MCP transport and authentication. Use `Authorization: Bearer <access token>` only if the server specifies bearer authentication. Verify endpoint identity and certificate validation; require HTTPS except explicitly approved loopback HTTP. Never forward credentials to unapproved endpoints or redirects, or use a token embedded in a URL/query string.
6. If the client cannot add a connection dynamically, guide the user through its own MCP setup and required reload/restart. Do not create vendor-specific configuration in this repository. Obtain permission before changing external host settings, preserve unrelated settings, and do not grant blanket tool permissions.
7. Discover the newly exposed tools and repeat the authenticated read-only verification. Report an MT5 account connected only when actual account access succeeds, then follow the handoff below.

Do not assume any particular environment-variable interpolation syntax, JSON configuration format, slash command, secret UI, or automatic `.env` loading. A config edit is not a connection. Do not install a trading bridge or call ad-hoc price/order HTTP endpoints as a fallback.

## Post-Connection Handoff

For a request to connect or reconnect to the MT5 MCP without a connection/status-only qualification, once authenticated read-only access verifies the account login plus broker server, demo/live type, and currency, report that identity and continue to the next incomplete onboarding step in the same response. Accept the monetary budget and target together; ask only for missing or ambiguous amounts/currency under [Monetary Risk And SQLite/Helper Contract](risk-management.md). These are the only user-supplied trading settings. This also applies when reusing an already-working connection. Do not end with only "connected", require a separate setup request, or ask whether to begin collecting inputs. Honor the explicit read-only exceptions in `AGENTS.md` without starting onboarding.

For trading onboarding, reconcile existing `ace_state.sqlite3` through `scripts/account_check.py` before reusing or updating saved inputs. Reuse verified same-account monetary drafts only as drafts, and verify real approval provenance before reusing a mandate. A missing database is unconfigured; a different account binding or corrupt/unsupported state requires the risk instructions' recovery rules, not silent replacement or copied approval. No legacy account-file detection or import is part of this workflow. Transport connectivity, configuration, or a health response without authenticated account verification must not trigger account-bound setup; report failed verification or missing MCP/secure-secret capabilities as connection blockers.

Missing broker/instrument calendars, market data, or execution capabilities does not by itself prevent collecting unapproved monetary drafts for the verified account. Report those blockers and keep new exposure blocked; connection or input collection alone never establishes approval. Include the compact [progress report](goals.md), with actual source timestamps, unavailable metrics clearly marked, monetary budget/target status and persistent latches/closure state, and `Next Permitted Step` identifying the requested input or blocker. Do not delay previously approved, identity-verified management/emergency reductions for onboarding questions or helper/database repair.

## Market Data And Instrument Discovery

Market analysis uses documented read-only MCP tools only. A quote, bar, or symbol-inventory read must be an actual authenticated response with its source timestamp; configuration, a health response, or an earlier session's memory verifies nothing.

1. List the broker's tradable symbols and keep the majors, major minors, metals, oil and other commodities, indices, and synthetics that actually exist on this account. Typical candidates include the major FX pairs, liquid minors such as EURJPY, GBPJPY, and AUDJPY, spot metals such as XAUUSD and XAGUSD, energy contracts such as WTI/Brent, index CFDs, and the broker's synthetic instruments.
2. For each candidate, verify asset/contract type, contract size, tick value and precision, account-currency conversion, volume minimum/maximum/step, stop and freeze distances, typical spread, commission, swap/financing, current margin requirement, and trading availability.
3. Read current quotes and the timeframes needed to describe the market: direction or range, higher-timeframe bias, momentum, volatility, spread quality relative to the planned stop, session, and any scheduled event that could invalidate the read.
4. Exclude symbols whose economics, conversion, or protective-stop support cannot be verified. Class-level scope is not per-symbol approval. Do not infer contract type, affordability, conversion, or market hours from a symbol name, assume a single forex calendar across asset classes, or assume 24/7 trading outside verified crypto/CFD hours.

Prices must come through actual documented MT5 MCP operations, not ad-hoc endpoints or a credential-bearing Python bridge. Unknown costs are not zero. Missing essential economics, minimum-lot affordability, or execution capabilities block the affected entry, not the whole analysis.

## Secret Handling

- Tokens must never enter SQLite, Markdown, Git, repository files, reports, URLs, or diagnostic logs. Do not print secret environment values or resolved host configuration just to check connectivity.
- Redact authentication headers and sensitive query values from errors before reporting. Request only the endpoint and authentication needed for this MT5 server, not unrelated credentials.
- If a user pastes a token into chat, do not repeat or persist it. Advise rotation if it has been exposed and request secure replacement. Do not claim that prior chat/log exposure has been erased.
- An ignored credential file is not a secure secret store. Keep actual credentials outside this repository and within the user's trusted client mechanism.

## Capability Verification

Before trading account approval or resumption, collect verified values and timestamps for these capabilities. Missing information permits setup/reporting, not new exposure. Approval must cover the exact named account, the approved instrument universe, the budget/target baselines, normal management, and both whole-account closure mandates, including manual exposure and the observed-only limitation.

| Account identity | Account login and broker server together, demo/live type, account currency, authenticated terminal/account status. Confirm the whole named account and approved scope; the monetary allowance does not segregate funds, even if equity is much larger. |
| Account telemetry | Current balance, equity, floating P&L, margin and free margin, source timestamps, and health of quote/account feeds. |
| Timing / observation | Verified source times, timezone/DST interpretation, freshness bounds, and coherent account/history boundaries. Do not infer broker timezone from the host clock or demand reconstructed unseen peaks or midnight equity. The allowance has no daily reset. |

| Accounting | Deal/order history, unique event IDs or reliable cursors, gross/net and signed cost semantics, commissions, swaps, fees, partial closes, corrections/deferred postings, and verified external cash-flow classification for separate policy/goal windows. Reconcile starting equity and history boundaries; a deposit in equity but missing from lagging history is not profit or a new adjusted peak. Estimate incremental closing costs without deducting costs already in equity twice. |

Read only the capabilities actually exposed. If a required value or mutation's targeting/result semantics cannot be verified, identify that blocker rather than inventing an implementation. Read-only credentials cannot execute trades; do not silently escalate access or build a new runtime service. There is no independent continuous guard, required server goal-admission service, or claim of server fencing. The local helper checks supplied snapshots only while the AI is active; it cannot guarantee a cap, return, continuous observation, or cancellation latency.

## MCP Execution And Local Intents

Verify how each actual MCP mutation targets the approved login plus broker server, demo/live type, and currency. Use documented account identifiers or account-scoped connection semantics where provided and reverify the intended account before dispatch and on readback. Do not assume a default-current-account tool is safely targeted when the account or its semantics are unknown; an identity mismatch blocks that action. One active account and one local trading-agent writer are required, with ownership reverified on resumption. A read followed by local preparation cannot prevent a later terminal account switch or concurrent manual trade.

The agent, not the helper, obtains actual MCP data and verifies approval provenance. Use `scripts/account_check.py` with repository-root `ace_state.sqlite3` according to [the exact JSON/SQLite contract](risk-management.md); do not invent fields, edit SQL to manufacture authority, or treat an asserted verification flag as evidence. The helper performs no networking or trading. SQLite transactions reserve recorded headroom and one exact intention locally, not broker execution; they cannot fence other repositories/manual traders or make the check-to-dispatch interval atomic.

1. On every active decision cycle, obtain a fresh verified account/exposure/history snapshot and call `check`, even without an entry signal. Reconcile coherent cash-flow windows, observed peak, latches, closing costs, one-writer ownership, and unresolved intents. A check reports state; it is not a reusable order authorization.
2. For an eligible risk increase under the approved mandate, verify the current market read, account-wide stressed risk, broker stops, sizing/margin/costs, and exact parameters. Run a fresh `prepare` and verify durable local recording of the action and its account/policy/goal/symbol binding before dispatch. Do not prepare competing risk increases or silently change a prepared action.
3. Successful preparation under the approved mandate permits the actual documented MCP market/pending order or approved modification, cancellation, or close. Execute that exact action without a separate per-trade user confirmation; client tool permissions still apply. Do not stop at a passing calculation, claim execution without a tool result, invent a tool, or bypass denied access with ad-hoc HTTP.
4. Obtain post-action broker readback and verify order/ticket status, actual fills, stops, volume, remaining pending orders, and relevant history. Call `resolve` with verified outcomes; a submission acknowledgment alone is not a fill, cancellation, or flat account. Unknown outcomes and partial fills with unverified remainders stay unresolved and block further risk increases.

Normal modifications/cancellations/closes must stay within approved management rules. Previously authorized identity-verified safety reductions do not require an entry signal or permission to add risk. Preserve original position/order bindings; classify manual exposure honestly under the whole-account closure mandate rather than inventing an owner. Use local preparation/recording when available, but helper/database failure must not delay an already-authorized identity-verified emergency reduction. Verify documented tickets/remaining-volume semantics, avoid duplicating uncertain actions, and reconcile the local record as soon as possible.

On every startup/resumption, recover unresolved local intents and in-flight broker requests with their original account/goal/symbol/signal binding before new exposure. An empty order list does not prove that a pre-crash request never executed or cannot execute later. Reconcile actual orders, deals, positions and authoritative documented status; do not create a replacement action ID or retry an ambiguous dispatch merely because no immediate fill is visible. Missing recovery evidence blocks further risk increases, not a separately authorized and safely targeted emergency reduction.

## Whole-Account Stops

At an observed drawdown greater than or equal to the monetary budget, or estimated account equity gain after cash-flow adjustment and incremental close costs greater than or equal to the target, latch off new risk. Under the approved mandate, cancel ALL account pending entries and close ALL account positions, including manual/other-origin exposure. Preserve protective orders until the related positions are safely closed, then reconcile remaining/orphan orders and late fills. Loss-stop handling takes precedence if both triggers apply; no entry signal is needed to perform these already-approved closures.

Read back actual cancellations, partial fills, remaining volumes/stops and positions. Account completion requires verified flat exposure, no remaining pending orders, and reconciled in-flight intents, not a submitted close request. Report trigger time, pending closure, verified final net result, and any target shortfall separately under [Goals And Progress](goals.md). A target latch remains set even if slippage or late costs leave final profit below target. Reconnects, new days, equity recovery or accounting corrections never release either stop.

A new goal requires explicit named-account approval and reconciliation of old intents/exposure/costs before activation. Follow the helper contract's settlement requirements before replacing a goal/policy; never close exposure merely to manufacture a new baseline without existing authority. A same-policy new goal preserves the risk cash-flow anchor and observed peak and cannot release a loss latch. A risk-policy reset requires explicitly approved replacement and retained audit history, not a new draft, missing file, or SQL edit. There is no independent service acting while the AI is inactive; observed peaks/breaches can be missed and broker stops cannot guarantee either monetary threshold.

## Reconnection And Uncertain Results

On any authentication failure, permission rejection, stale required feed, disconnect, account switch, unknown connection state, unavailable helper/state, unresolved mutation, or persistent stop, do not submit risk-increasing actions. Report blockers with last verified timestamps and stop/closure state separately. Existing approved management/emergency reductions remain permitted only on a positively verified account, through documented safely targeted tools; they do not require an entry signal or active entry permission. No continuous protection service is implied during the outage.

After reconnecting for trading, reverify identity/currency, instrument calendars, exposure/protection, coherent account/cash-flow/cost history, current market data, local ownership, SQLite bindings/latches, actual approval provenance, and every unresolved intent. Obtain a fresh snapshot and `check`; cached `status` is not present verification. Preserve observed peaks and anchors without reconstructing unobserved continuous equity or broker-midnight values. Reconnection is not a new goal or policy reset. Missing/invalid state blocks entries rather than authorizing a fresh baseline.

For any mutation that times out, is interrupted, or returns an ambiguous acknowledgment:

1. Treat its execution status as unknown, not failed or successful. Freeze further risk-increasing actions.
2. Recover the durable local intent with its original account/owner/goal/symbol/signal binding and reconcile broker orders, positions, and deals using its submitted ticket/client identifier and documented result semantics, including still-in-flight requests. Request authoritative status if the result remains ambiguous; never relabel it to a new goal or symbol.
3. Retry only when the actual state and the server's documented idempotency/remaining-volume rules make the operation safe. Never blindly duplicate an entry or a close.
4. Verify actual pending-order scope/cancellation, modifications/protective stops, and position closure/remaining volume by readback, then reconcile through `resolve`. Never assume an opposite order closes a position; it may create hedged exposure or reverse a net position.
5. If liquidation is rejected, partially filled, or unavailable, report unresolved exposure and continue only verified, bounded safety actions. Do not claim that the account is flat or that a drawdown cap was preserved.

The client's permission system is a separate execution gate. Account/goal approval does not bypass it. Explain blocked tool-specific access without enabling all tools, treating a denied action as completed, or imposing routine extra per-trade user approval on an otherwise approved eligible action.
